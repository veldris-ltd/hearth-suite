# Internationalisation: v1.0 scope decision

**Status:** Decided, 2026-06-09. **Scope for v1.0: English (`en`) only.**

Hearth Suite v1.0 ships with a single, hard-coded English user interface. There is no
runtime locale switch and no translated message catalogs in this release. This
is a deliberate, recorded scope decision (closing audit item P2-Q2), not an
oversight.

## Why English-only for v1.0

- **Focus the launch.** v1.0 is the open-source debut; the priority is a correct,
  secure, offline-first product on five platforms. A full localisation programme
  (catalogs, a translation pipeline, per-locale QA, pluralisation/date/number
  formatting, and locale-aware Ember prompts) is a cross-cutting effort better
  done deliberately than rushed for launch.
- **Honesty over a token gesture.** Shipping one half-translated locale would
  misrepresent the product's language support. We would rather state the scope
  plainly than imply broader coverage than we have verified.
- **No user data is locale-gated.** Documents, Records, and Bundles are the
  user's own content in whatever language they write; nothing in the data model
  assumes English. Only the chrome (menus, labels, help copy) is English.

## What is already in place (so future i18n is cheap)

The groundwork is intentionally i18n-friendly, so externalising strings later is
additive rather than a rewrite:

- **RTL-ready layout.** Styling uses CSS *logical properties*
  (`inline-size`, `margin-inline`, `inset-inline-start`, `text-align: start`, …)
  rather than physical left/right throughout the design system and apps, so a
  `dir="rtl"` document reflows correctly without layout changes.
- **A single document-language declaration.** Every app page sets
  `<html lang="en">` in one place per app, the natural hook for a future locale.
- **Centralised UI copy surfaces.** Most user-facing strings live in the shared
  packages (`@hearth/design-system`, `@hearth/client-shell`, the module apps),
  which is where a `t()`/catalog layer would be introduced.

## Deferred plan (post-1.0)

Internationalisation is deferred to a **post-1.0 milestone** (tracked under
`docs/roadmap/`). When taken up, the intended shape is:

1. Introduce a tiny `t(key, vars)` lookup over per-locale JSON catalogs (no heavy
   framework), defaulting to `en`.
2. Externalise UI strings package by package into the catalogs.
3. Add a runtime locale switch that sets `<html lang>`/`dir` and reloads copy.
4. Prove a second locale end to end, including at least one **RTL** locale, with
   an RTL layout smoke test added to the E2E suite.

Until then, the supported UI language is English, and this document is the
record of that decision.
